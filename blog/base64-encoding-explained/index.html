Base64 Encoding Explained

Published: May 6, 2026 Reading Time: 5 min

Base64 encoding is one of those technologies every developer uses daily but few stop to understand. It sits quietly inside data URIs, JWT tokens, email attachments and API payloads — converting binary data into safe, printable text. This guide explains exactly what Base64 does, why it makes files roughly 33% larger, and why treating it as encryption is a dangerous mistake.

1. What Is Base64 Encoding, Exactly?

Base64 is a binary-to-text encoding scheme. It takes any sequence of bytes — an image, a PDF, a cryptographic key — and represents it using only 64 printable ASCII characters: A-Z, a-z, 0-9, plus + and /, with = reserved for padding. Because every one of those 64 characters fits comfortably into plain text systems, the encoded output can travel through channels that were never designed for raw binary data, such as JSON, XML, URLs and email bodies.

The key insight is that Base64 is a representation, not a transformation. Encode a file and decode it again, and you get back the exact same bytes, bit for bit. Nothing is compressed, nothing is hidden, and nothing is protected.

2. Why Base64 Exists: The 6-Bit Problem

The maths behind Base64 is elegant. Text protocols historically assumed 7-bit ASCII, but binary files use all 8 bits per byte, including control characters that can corrupt or terminate a text stream. Base64 solves this by regrouping the data: every 3 bytes (24 bits) are split into four 6-bit chunks, and each 6-bit chunk maps to one of the 64 safe characters.

That regrouping explains the famous 33% size overhead: 3 bytes become 4 characters, so the encoded output is always roughly one-third larger than the original. If the input length is not a multiple of three, one or two = padding characters are added at the end — which is why so many Base64 strings finish with = or ==.

"Base64 was never designed to make data smaller or safer. It exists for one reason only: to make binary data survive transport through systems built for plain text."

3. Base64 Is Not Encryption — And Never Will Be

This is the single most important security lesson in this guide. Base64 has no key, no secrecy and no protection. Anyone who sees a Base64 string can decode it instantly with free tools — including our own Base64 encoder and decoder. Yet production systems are still breached because developers Base64-encode passwords, tokens or personal data and assume the result is "scrambled".

If data needs confidentiality, use real cryptography: AES for symmetric encryption, TLS for data in transit, and bcrypt or Argon2 for password hashing. Base64's correct security role is supporting cast — for example, safely carrying encrypted bytes or hash digests inside text formats. It encodes; it does not protect.

4. Where You Meet Base64 in Real Projects

  • Data URIs: Small images and fonts embedded directly in CSS or HTML as data:image/png;base64,..., saving an HTTP request at the cost of caching flexibility.
  • JWT tokens: The header and payload of a JSON Web Token use Base64URL — a URL-safe variant that swaps + and / for - and _. Paste any token into our JWT decoder and you will see the JSON appear instantly, which proves again that encoding is not encryption.
  • Email attachments: The MIME standard encodes attachments in Base64 so binary files survive mail servers that expect 7-bit text.
  • API authentication: HTTP Basic Auth joins the username and password with a colon, then Base64-encodes them into the Authorization header — safe over HTTPS, hopeless without it.

5. The 33% Size Tax: When to Avoid Base64

Because Base64 inflates every file by a third, embedding large assets is an anti-pattern. A 500 KB photograph becomes roughly 665 KB of text that cannot be cached separately and blocks rendering while the browser parses it. Reserve data URIs for tiny assets under about 10 KB — icons, placeholders and inline SVG fallbacks — and serve everything else as normal files. If page weight is a concern, run your assets through the free image compressor before even thinking about embedding them.

Frequently Asked Questions

Q: Is Base64 encoding secure for hiding passwords?

No. Base64 is fully reversible by anyone in seconds and provides zero secrecy. Passwords should be hashed with bcrypt, scrypt or Argon2 — never encoded or encrypted reversibly.

Q: Why does Base64 make files about 33% bigger?

Every 3 bytes of input are regrouped into four 6-bit chunks, each stored as one full character. Four characters replace three bytes, so output size is always about 4/3 of the original.

Q: What is the difference between Base64 and Base64URL?

Base64URL replaces the + and / characters with - and _ and usually omits = padding, making the string safe to place inside URLs and filenames. JWT tokens use this variant.

Q: Can I decode Base64 without sending data to a server?

Yes. Browser-based tools like the OmniTools Base64 encoder/decoder decode everything locally with JavaScript, so your data never touches a remote server.
